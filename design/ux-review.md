# 輕量 UX 走查

## 產品理解與任務

從首頁可見內容判斷，這是給中文使用者的英語單字與考試題型練習工具；使用者可從每日目標開始一輪練習、確認答案，再複習錯題。

自行選擇的主要任務：從「今天」開始一輪預設單字練習，回答所有題目並確認本次成果。**已完成**。未檢視應用程式來源碼。

環境：Edge／Playwright，手機視窗 390 × 844 為主；1440 × 1000 補看首頁及第一題。入口 `http://127.0.0.1:5173/app?demo=1`，全程使用新瀏覽器 context 的虛構 demo 資料。

## 實際路徑

1. 首頁看到「今日目標 12 / 20 題」與高對比「開始練習」→ 理解為繼續今天的學習 → 點擊後出現「練什麼」底部面板。沒有卡住。
2. 面板預選單字複習、英選中、全部、20 題 → 沿用預設開始 → 進入單字與四個中文答案的題目頁。題型、範圍、題數皆可見，開始按鈕明確。
3. 看到題目與四個選項 → 選一個答案，再按「確認答案」→ 選中答案後才可確認；確認後顯示對錯、正確答案與其他選項對應單字，底部按鈕改為「下一題」。紅綠之外也有文字及勾叉回饋，知道作答已完成。
4. 依序完成 20 題 → 前 19 題使用「下一題」，第 20 題使用「查看結果」→ 進入本次結果，顯示 35% 正確率、0 跳過、0 標記、錯題及重做／重新開始／回今天動作。為驗證完整路徑，本輪每題固定選 A，並非模擬真實知識能力。

證據：[首頁](ux-entry.png)、[設定面板](ux-start.png)、[題目](ux-question.png)、[答錯回饋](ux-feedback.png)、[結果](ux-result.png)、[桌面首頁](ux-desktop-entry.png)、[桌面題目](ux-desktop-question.png)。截圖為 full-page；結果截圖高度超過單一手機視窗。

## 關鍵問題（兩項）

### 1. 結果主數字的含義需要推算（猶豫）

**觀察到的事實：** 完成全部 20 題並按「查看結果」後，結果主卡寫「這次完成了」，中央大字為 `7 / 20 題`，下方另有 `35% 正確率`。本輪實際回答 20 題，7 是答對題數；但主數字旁沒有「答對」標籤。今日目標已變為 `32 / 20`，亦可見本輪作答 20 題已計入。證據：`ux-result.png`。

**原因推斷：** 完成敘述與正確題數共用一個視覺群組，容易先理解為只完成七題，再透過下方正確率反推含義。

**建議達到的結果：** 使用者一眼能分清「完成 20 題」和「答對 7 題」，無需用百分比計算。

### 2. 作答途中難以準確知道還剩幾題（猶豫）

**觀察到的事實：** 手機題目頁頂部用一排細小圓點表示 20 題進度，頁面沒有「第 n / 20 題」文字。相同現象也出現在桌面第一題。需靠數圓點判斷具體進度；最後一題直到確認答案後，按鈕才由「下一題」改為「查看結果」。證據：`ux-question.png`、`ux-desktop-question.png`；實際完整走到第 20 題。

**原因推斷：** 圓點可表達整體進度，但精確剩餘量不易讀取，尤其是手機的一長排小點。

**建議達到的結果：** 保留圓點的快速概覽，同時讓使用者直接讀到目前題號與總題數。

## 資料與工具限制

- Demo 的本輪 20 題包含重複單字；結果清單也出現重複的 candid、obsolete、abandon。這只證明此次虛構資料及本輪輸出有重複，不能據此判定正式資料或出題規則有缺陷，未列為產品問題。
- 最初一次自動化嘗試把第一題的單字、答案順序寫死；新 context 隨機抽題後該定位失敗。改以當前畫面選項完成流程；這是測試腳本假設造成的工具問題，不是產品卡住。
- 沒有走錯或阻斷。完成回饋清楚；上述問題是理解與進度判讀上的猶豫。
- 未驗證登入、同步、其他題型、網路失敗、錯題重做後的資料變化、真機觸控／長按／震動，以及聲音。未觸發對外訊息或真實帳號流程；不對真實使用者成功率、滿意度或耗時下結論。
